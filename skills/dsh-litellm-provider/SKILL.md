# Configure DSH with Local LiteLLM Proxy Provider

Set up DeepSeek Harness to use a **local LiteLLM proxy** as a custom
OpenAI-compatible provider. This writes the provider configuration to
DSH's `settings.yaml` so the Claude models served by LiteLLM (via
Vertex AI) are available as model routes in the DSH WebUI.

For DSH installation, see the `dsh-setup` skill first.

## Prerequisites

- LiteLLM proxy running locally at `http://127.0.0.1:4000`

  before proceeding

## Architecture

DSH stores settings in `~/.dsh/settings.yaml` (or `$DSH_HOME/settings.yaml`).
The `llm-pi-ai` plugin manages model providers. A custom provider needs:

| Field | Purpose |
|-------|----------|
| `baseURL` | LiteLLM endpoint: `http://127.0.0.1:4000/v1` |
| `api` | Protocol: `openai-completions` |
| `apiKeyEnv` | Env var holding a dummy API key (DSH requires non-empty) |
| `models` | List of model IDs matching LiteLLM's `model_name` entries |
| `compat` | Protocol compatibility flags for LiteLLM |

DSH serves **only** the models listed in `settings.yaml`. Its "fetch available
models" action in Settings → Models is a one-off UI helper; nothing is stored
and there is no runtime discovery (`dsh-llm-pi-ai` discovery module). After a
proxy model refresh, re-run `setup.sh`.

The default model for new Agents lives in a separate top-level section,
`agent-default-model` (`provider` + `model`), read live by DSH.
`setup.sh` sets it to the strongest served model (`hey litellm default model`).

## Reference Configuration

**File:** `~/.dsh/settings.yaml` (relevant section)

> ⚠️ **Use this exact schema.** Do NOT write from memory or
> improvise field names. Copy this template and substitute only
> the marked placeholders.

```yaml
llm-pi-ai:
  providers:
    litellm-vertex-ai:
      apiKeyEnv: LITELLM_VERTEX_AI_API_KEY
      api: openai-completions
      baseURL: http://127.0.0.1:4000/v1
      compat:
        supportsDeveloperRole: false
        maxTokensField: max_tokens
      models:                     # generated by setup.sh from /v1/models
        - id: claude-opus-5       # (excerpt — one entry per proxy model;
          input: [text, image]    #  current list: `hey litellm model list`)
        - id: claude-sonnet-5-5
          input: [text, image]
        - id: claude-haiku-4-5
          input: [text, image]
agent-default-model:              # default for new Agents
  provider: litellm-vertex-ai
  model: claude-opus-5-5          # strongest served model
```

### Compatibility Flags

| Flag | Value | Why |
|------|-------|-----|
| `supportsDeveloperRole` | `false` | LiteLLM proxies `role: "developer"` as-is but Vertex AI Claude doesn't accept it. Forcing `false` makes DSH send `role: "system"` instead. |
| `maxTokensField` | `max_tokens` | LiteLLM uses the OpenAI `max_tokens` field, not `max_completion_tokens`. |

### Image Input

All Claude models served by the proxy support vision. The `input: [text, image]`
declaration on each model tells DSH to allow image attachments in the
WebUI for those models.

## Workflow

### Step 1 — Dry run, then apply

The agent MUST run the dry run first:

```bash
bash ~/.agents/skills/dsh-litellm-provider/scripts/setup.sh --dry-run
```

- `DRY_RUN_RESULT=CONVERGED` → nothing to change. Go to Step 2.
- `DRY_RUN_RESULT=PENDING` → show the `Changes:` list, then apply:

```bash
bash ~/.agents/skills/dsh-litellm-provider/scripts/setup.sh
```

| Flag | Effect |
|------|--------|
| `--default-model M` | Use `M` (must be served) instead of the strongest model |
| `--no-default` | Leave `agent-default-model` untouched |
| `--force-default` | Overwrite `agent-default-model` even when it points at another provider (skipped otherwise) |

The script writes a timestamped backup, replaces only the provider block and
`agent-default-model`, and refuses to write if anything else would change.
Restart DSH if it is running.

### Step 2 — Verify the configuration

The agent MUST run:

```bash
bash ~/.agents/skills/dsh-litellm-provider/scripts/verify.sh
```

### Step 3 — Restore (after DSH update)

If the user reports a lost provider after a DSH update, the agent MUST
re-run the setup script from Step 1. The script is idempotent.

## Output Contract

- setup.sh `--dry-run` → `DRY_RUN_RESULT=CONVERGED|PENDING` + `Changes:` list
- Exit 0 from setup.sh → provider configured successfully (prints backup path, model count, default)
- Exit 0 from verify.sh → configuration verified
- Exit 1 → error (LiteLLM unreachable, DSH not installed, etc.)

## Gotchas

- **`~/.dsh/` is created on first DSH launch.** If you run this skill
  before ever launching DSH, the directory won't exist. The setup
  script creates it if missing.
- **Model IDs must match exactly** between LiteLLM's `config.yaml`
  (`model_name`) and this provider's `models[].id`. The setup script
  auto-discovers them from the running proxy.
- **Dummy API key required.** The local LiteLLM proxy has no
  authentication, but DSH rejects providers with an empty API key.
  The setup script sets `apiKeyEnv: LITELLM_VERTEX_AI_API_KEY`; the value
  (`sk-litellm-local-no-auth`) must be in the environment DSH launches with —
  `dsh-setup`'s `install-desktop.sh` sets it on the desktop service.
- **No runtime model discovery.** Unlike Hermes, DSH does not pick up new
  proxy models by itself — `verify.sh` "Model sync" failing after
  `refresh litellm models` is real; re-run `setup.sh`.
- **`supportsDeveloperRole: false` is critical.** Without this flag,
  DSH sends `role: "developer"` for system prompts, which Vertex AI
  Claude rejects through LiteLLM.
- **Settings format may change.** DSH is in developer preview. The
  `llm-pi-ai` plugin's settings schema could change across versions.
  The setup script includes a version check and warns if the expected
  structure is missing.
